# Расписание и политика хранения

`/schedule` определяет, **когда** делаются бэкапы. `/retention` определяет, **сколько** их хранится.

## Расписание

```
/schedule 1 03:00
          │   │
          │   └── время: 03:00
          └────── интервал в днях: каждый день
```

| Команда | Значение |
|---|---|
| `/schedule 1 03:00` | Каждый день в 03:00 |
| `/schedule 2 03:00` | Через день в 03:00 |
| `/schedule 7 04:00` | Раз в неделю в 04:00 |
| `/schedule 30 04:00` | Примерно раз в месяц |
| `/schedule off` | Без автоматических бэкапов |

Интервал может быть от 1 до 365 дней. Кнопки в `/backup` → **📅 Расписание** (Каждый день, Раз в 3 дня,
Раз в неделю, Выключить) меняют только интервал, время остаётся прежним.

> После установки расписание **выключено**. Пока вы не отправите `/schedule`, бэкапы делаются только
> по кнопке **Бэкап сейчас**.

Для серверов, данные которых меняются каждый день (сайты, базы, загрузки), лучший выбор —
`/schedule 1`: благодаря дедупликации ежедневный бэкап добавляет только изменения.

### Как это работает

1. Когда вы задаёте расписание, vps-alert вычисляет следующий запуск, то есть первое подходящее время
   после текущего момента, и сохраняет его в `/var/lib/vps-alert/settings.json`.
2. Сервис проверяет часы каждые 30 секунд.
3. Когда время наступает, он сначала сохраняет время следующего запуска, а потом начинает бэкап. Если
   сервер упадёт посреди бэкапа, после перезагрузки этот же запуск не начнётся снова.

Следующий запуск показан в меню `/backup` (**⏭ Следующий**) и в ежедневном отчёте.

| Ситуация | Что происходит |
|---|---|
| Сервис перезапустился | Расписание продолжается: оно хранится на диске |
| В момент бэкапа сервер был выключен | Как только он включится, выполняется один бэкап, дальше расписание идёт как обычно. Неделя простоя — это один бэкап, а не семь |
| В запланированное время ещё идёт бэкап, запущенный вручную | Запланированный пропускается, следующий выполнится вовремя |
| Нажата **Бэкап сейчас** | На расписание не влияет |

### Часовой пояс

Время берётся по часовому поясу **сервера**, а многие VPS работают в UTC. Проверить и изменить:

```sh
timedatectl
sudo timedatectl set-timezone Europe/Moscow
sudo systemctl restart vps-alert
```

После этого снова отправьте `/schedule`, чтобы следующий запуск был рассчитан в новом поясе.

## Политика хранения (retention)

```
/retention 7 4 6
           │ │ └── ежемесячные: по одному за каждый из последних 6 месяцев
           │ └──── еженедельные: по одному за каждую из последних 4 недель
           └────── ежедневные:   по одному за каждый из последних 7 дней
```

После каждого бэкапа снапшоты, не подходящие ни под одно из этих правил, удаляются, поэтому место не
растёт бесконечно. В пределах каждого дня, недели или месяца сохраняется самый новый снапшот.

### Пример

Бэкапы каждый день, `/retention 7 4 6`, сегодня 25 октября:

| Правило | Что хранится |
|---|---|
| 7 ежедневных | 19, 20, 21, 22, 23, 24, 25 октября |
| 4 еженедельных | последний за каждую неделю: 25, 19, 12, 5 октября |
| 6 ежемесячных | последний за каждый месяц: 25 окт, 30 сен, 31 авг, 31 июл, 30 июн, 31 мая |

Один снапшот может подходить под несколько правил (25 октября есть во всех трёх), поэтому хранится
около 14 снапшотов, а не 17. Можно вернуться к любому дню последней недели, к любой неделе последнего
месяца и к любому месяцу последнего полугода.

Старые снапшоты важны, потому что проблемы не всегда замечают сразу. Если таблицу удалили три недели
назад, во всех ежедневных снапшотах её уже нет, а в еженедельном или ежемесячном она ещё есть.

### Место

14 снапшотов — это не 14 полных копий. Благодаря дедупликации серверу на 3 GB, который меняется на
50 MB в день, на все снапшоты нужно примерно 4–5 GB.

### Другие варианты

| Команда | Значение |
|---|---|
| `/retention 7 4 6` | По умолчанию: неделя ежедневных, месяц еженедельных, полгода ежемесячных |
| `/retention 14 8 12` | Больше истории: две недели, два месяца, год |
| `/retention 3 0 0` | Только последние 3 дня, когда мало места |
| `/retention 7 0 3` | Неделя ежедневных и 3 ежемесячных |

`0` выключает правило, но все три значения не могут быть `0` одновременно.

Строго говоря, «ежедневных 7» означает последние 7 *дней, в которые был снапшот*. Поэтому если бэкапы
делаются раз в 3 дня, `7` охватывает примерно три недели.

### Область действия

Политика хранения затрагивает только снапшоты, сделанные vps-alert на этом сервере: они помечены
тегом `vps-alert` и именем сервера. Другие снапшоты restic в том же репозитории не трогаются. Если
изменить `SERVER_NAME`, снапшоты со старым именем больше не будут удаляться автоматически.
