# Базы данных

Если просто скопировать файлы работающей базы, можно сохранить их в недописанном состоянии. Поэтому
vps-alert перед бэкапом выгружает каждую базу в согласованный `.sql` файл.

## Выбор баз

Отправьте `/db` (или нажмите **🗄 Базы данных** в `/backup`). vps-alert ищет:

| Где | Как находится |
|---|---|
| PostgreSQL на сервере | установлен `psql` и есть системный пользователь `postgres` |
| MySQL / MariaDB на сервере | установлен `mysqld` или `mariadbd` |
| Docker-контейнеры | работающие контейнеры с образом `postgres`, `postgis`, `timescale`, `pgvector`, `mysql`, `mariadb` или `percona` |

Бот показывает все базы, к которым удалось подключиться. Нажатие переключает базу между ✅ (в бэкапе) и
⬜ (пропускается):

```
✅ postgres · shop
✅ docker:api-db · api
⬜ docker:api-db · test
✅ mysql · wordpress
[🔄 Искать снова] [« Назад]
```

Системные базы (`postgres`, `mysql`, `sys`, `information_schema`, `performance_schema`) не показываются.
Выбранная база, которая пропала, отображается как *(не найдена)*, чтобы с неё можно было снять отметку.

## Во время бэкапа

- Каждая выбранная база выгружается в отдельный файл в `/var/lib/vps-alert/dumps/`, например
  `postgres/shop.sql` или `docker-api-db/api.sql`, вместе с описывающим их `manifest.json`.
- restic сохраняет эти файлы вместе с остальным бэкапом, после чего они удаляются с диска.
- Неудачная выгрузка отмечается ❌ и не останавливает остальные.

| СУБД | Команда выгрузки |
|---|---|
| PostgreSQL | `pg_dump` (обычный SQL) |
| MySQL / MariaDB | `mysqldump` / `mariadb-dump --single-transaction --routines --triggers --events` |

## Доступ без паролей

vps-alert не спрашивает пароли от баз. Он использует доступ, который уже есть у root:

- **PostgreSQL на сервере**: работает от имени системного пользователя `postgres` (peer authentication).
- **MySQL / MariaDB на сервере**: подключается как `root` через локальный сокет (так настроено по
  умолчанию в Debian и Ubuntu).
- **Docker**: запускает клиент внутри контейнера с данными, которые официальные образы хранят в своём
  окружении: `POSTGRES_USER`, `MYSQL_ROOT_PASSWORD`, `MARIADB_ROOT_PASSWORD` или их варианты `_FILE`.

Пароли от баз никогда не вводятся через бота, потому что они остались бы в истории чата.

### Если база не найдена

Предупреждения поиска показываются под списком. Частые причины:

- MySQL-контейнер запущен с `MYSQL_RANDOM_ROOT_PASSWORD`: пароля, который можно прочитать, нет.
- MySQL на сервере требует пароль root вместо входа через сокет.
- База удалённая или управляемая (RDS, Supabase, ...): её нет на этом сервере.

В таких случаях запишите в env-файл свою команду выгрузки, которая сохраняет в папку, добавленную через
`/paths add`:

```sh
BACKUP_PRE_COMMAND=PGPASSWORD=secret pg_dump -h db.example.com -U app app > /var/backups/db/app.sql
```

Она выполняется перед каждым бэкапом и задаётся только в env-файле, никогда через бота.

## Восстановление

`sudo vps-alert restore` → **A database** загружает дамп обратно. См. [восстановление](restore.md#база-данных).

## Известные ограничения

- Роли (пользователи) PostgreSQL не входят в `pg_dump`. При восстановлении на новый сервер, где этих
  ролей нет, появятся ошибки `role "..." does not exist`. Сначала создайте пользователей, затем
  восстановите снова.
- MongoDB, Redis и SQLite пока не определяются. Файлы SQLite внутри сохраняемых папок копируются как
  обычные файлы.
